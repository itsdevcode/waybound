## WAYBOUND Phase 4B — Social Mystery Partner & Security Hardening

### Summary of Changes

This PR delivers the complete 2-player cooperative mystery quest experience along with comprehensive security hardening and concurrency protections reviewed prior to merge.

#### 1. Security & Identity Proof Hardening
- **Removed Unauthenticated Session Endpoint**: Eliminated insecure `POST /api/v1/auth/session` that allowed issuing session tokens for arbitrary client-provided `user_id` values without identity verification.
- **Proof of Identity (Email OTP)**:
  - Implemented `POST /api/v1/auth/otp/request` and `POST /api/v1/auth/otp/verify`.
  - Generates cryptographically secure 6-digit numeric OTPs (`secrets.choice`).
  - Salted HMAC-SHA256 hashed storage in database with 10-minute expiry and 5-attempt brute-force protection.
  - Automatically provisions new explorer accounts upon first verified OTP or logs into existing accounts.
- **Demo Authentication Isolation**:
  - Replaced legacy session creation with isolated `POST /api/v1/auth/demo-session`.
  - Restricted strictly to the seeded demo explorer (`DEMO_USER_ID`); rejects all arbitrary user IDs with `403 Forbidden`.
  - Disabled in production environments (`ALLOW_DEMO_AUTH=false` or `ENVIRONMENT=production`), returning `403 Forbidden`.
- **Session Revocation & Logout**:
  - Added `POST /api/v1/auth/logout` endpoint that revokes the caller's active session in the database immediately.
- **Sliding-Window Rate Limiting**:
  - Implemented in-memory sliding-window rate limiter on all authentication endpoints (`/auth/otp/request`, `/auth/otp/verify`, `/auth/demo-session`, `/auth/logout`) returning `429 Too Many Requests` when limits are exceeded.
- **Production Secret Validation**:
  - Enforced strict startup validation via `validate_production_security()`: in `production`, non-random or short `AUTH_SECRET` (< 32 characters) immediately halts startup.
- **Frontend Token Safety**:
  - Updated Next.js API client and state management: client cannot use saved `user_id` alone to authenticate.
  - Added automatic token removal on `401 Unauthorized` responses.

#### 2. Concurrency & Multiplayer Hardening
- **Decoupled AI/Places API from Database Row Locks**:
  - Refactored `start_cooperative_quest` to use a two-phase reservation pattern:
    1. Fast atomic transaction sets `party.status = "generating_quest"` using `with_for_update()`, preventing concurrent quest creation.
    2. Database connection is closed/committed before executing external Google Places API and Gemma model calls.
    3. Final atomic transaction persists `PartyQuest` and complementary `SplitClue` records, updating party to `active`.
  - In case of failure during generation, status cleanly reverts back to `open`.
- **Alembic Migrations**:
  - `a8220599a32a_create_parties_and_sessions.py`: Creates `parties`, `party_memberships`, `party_quests`, `split_clues`, `member_verifications`, and `user_sessions`.
  - `d7d7fb84a256_create_email_otps_table.py`: Creates `email_otps` table with index on email and expiration.
  - `604c5bfb88ca_allow_generating_quest_status_in_.py`: Updates check constraint `ck_parties_status_valid` to allow `generating_quest`.
- **Location-Grounded Split Clues**:
  - Validates that generated clues are complementary and location-grounded (architectural vs botanical/spatial perspectives).
  - Explicitly rejects fabricating generic environmental filler.
- **Privacy & Anti-Exploit XP Enforcement**:
  - Verified party/quest responses never disclose partner GPS coordinates, personal data, or hidden destination secrets.
  - Verification awards XP at most once per member.
  - Real-world quests award `0 XP` without trusted observation ground truth, preserving Phase 2 anti-exploit rules.
  - Mutual identity consent required before real names are revealed; either player can revoke consent at any time.
